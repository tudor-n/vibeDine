Accessibility
suggestions.

A set of suggested directions — not prescriptions — for making the Clarifi admin more accessible without losing its visual character. Treat each item as a starting point; pick the trade-offs that fit the codebase.

01 · Type

Reading & legibility

Body copy, eyebrows, mono labels — the everyday text load of the app.

The current ramp leans on small mono labels (11px / .18em tracking) and ink at .62 opacity for secondary text. Both are technically fine on a calibrated monitor and tough in real restaurant lighting. A few light moves would buy meaningful headroom.

type · bodyHigh

Consider a 16px body baseline

14–15px reads thin at arm's length on a tablet — particularly for staff over 40 working under warm restaurant lighting.

Possible directions
  • Bump the default --text-body token to 16px, let larger surfaces inherit
  • Or scope per surface: dashboards & menus stay where they are, dense logs go to 16
type · contrastHigh

Lift secondary ink above AA

rgba(21,20,15,.62) on the paper background falls just below 4.5:1 at body sizes. A small bump fixes it without changing the look.

Possible directions
  • Try --ink70 at .70–.72 for body, reserve .62 for purely decorative meta
  • Audit the .metric-foot / .lede usages where small + faded combine
type · eyebrowsMedium

Soften mono eyebrows for content roles

11px JetBrains Mono in .18em uppercase is a great brand signature on chrome and tags, but doubles the cognitive load when used as a section label inside a content area.

Possible directions
  • Keep mono eyebrows on framing chrome (status pills, frame tags, debug meta)
  • For in-content section labels, try 12–13px / .12em tracking, or sentence-case sans
  • Distinguish the two roles in the design tokens, not at call sites
type · displayLow

Loosen display line-height a hair

Hero titles run at line-height:.95. Dramatic, but descenders kiss the next line on multi-line headings. 1.0–1.05 still reads as a tight display.

Possible directions
  • Set line-height: 1 as the new floor for .display-title
  • Pair with a letter-spacing nudge from −0.04 to −0.035 to keep the visual weight
02 · Interaction

Hit targets & focus

What staff tap, click and tab through during a busy service.

The visual system is generous with whitespace, but several interactive elements (filter chips, icon buttons, the rule-row close button) sit below the 44×44 minimum. Easy wins, mostly.

tap · targetsHigh

Bring all controls to ≥ 44×44

The orders filter chips are 36px tall; the rule-row delete button is 38×38. WCAG 2.2 SC 2.5.8 asks for 24×24 minimum, but the platform conventions (iOS HIG, Material) recommend 44.

Possible directions
  • Add a --tap-min: 44px token, apply via min-height/min-width on chip & icon-button mixins
  • Or keep visual size but extend the hit area with ::before overlays
focus · ringHigh

Define a single global focus ring

Browser default focus is partially hidden by the pill backgrounds and dark surfaces. A consistent :focus-visible treatment across all interactive primitives would help keyboard users navigate.

Possible directions
  • 3px outline using --accent with 2px offset, applied via a global :focus-visible mixin
  • For dark surfaces, switch the ring to --lime via a CSS variable cascade
  • Never disable focus styles to hide click halos — gate via :focus-visible instead
keyboard · navMedium

Audit tab order & roles

Several pill-shaped controls (filter chips, nav links) are <button> visually but rendered as <div> or <span> in the markup, breaking keyboard nav and screen readers.

Possible directions
  • Promote interactive pills to real <button> / <a> elements
  • For toggle chips, mirror the visual state with aria-pressed
  • For the order-status badges, use role="status" + aria-live="polite" when state changes during service
motionLow

Honor prefers-reduced-motion

The bloom backgrounds animate subtly; some staff and customers will have motion sensitivity. A single media-query gate handles it.

Possible directions
  • Wrap any keyframe / transition longer than ~150ms in @media (prefers-reduced-motion: no-preference)
  • For the live-dot pulse, swap to a static glow when reduced
03 · Structure

Semantics & assistive tech

How the DOM reads to a screen reader, regardless of visual styling.

The visual hierarchy is clear; the underlying HTML doesn't always match. Worth a quick audit, especially since the marketing-style mono labels can read strangely when announced literally.

aria · landmarksMedium

Wrap shells in semantic landmarks

The admin layout is <div>-driven. Adding <nav>, <main>, <header> would let assistive tech jump between regions.

Possible directions
  • One <main> per route, one <nav aria-label="Admin"> for the side rail
  • Promote the page-level eyebrow + h1 into a single <header> region
aria · labelsMedium

Give icon-only buttons accessible names

The ✕ delete button on rule rows announces as "X" to screen readers. Same for the live-dot tag pills.

Possible directions
  • Add aria-label on icon buttons ("Șterge regula", "Live, sala 1")
  • Or wrap the symbol with aria-hidden="true" and append a visually-hidden text node
screen-reader · metaLow

Reconsider how mono meta strings get announced

Strings like impressions · table-side, claim / shown, scope · sala 1 read beautifully but make for awkward voiceover. They mix English keywords with Romanian content, and the · separator gets announced as "middle dot".

Possible directions
  • Keep the mono label visually, but provide a aria-label with a natural-language equivalent: "afișări la masă", "scope camera 1"
  • Or: hide truly decorative meta from AT entirely with aria-hidden, and surface the same info as a tooltip / inspector for sighted users only
  • Choose one language per content surface — mixing English UX-jargon with Romanian copy is a tax on every reader, sighted or not
04 · Color

Surfaces & state

Where color carries meaning, not just brand.

The accent / lime / ink palette is strong and recognizable. Watch for places where color is the only signal, and edges that fall below 3:1 contrast against their surrounds.

color · bordersMedium

Card borders may be too soft

--ink12 at .10–.12 opacity reads as a hairline; on the warm paper background it can vanish entirely under glare.

Possible directions
  • Try --ink12 at .14–.16 globally — borders stay subtle, cards stay separable
  • Or rely more on shadow + spacing than borders for card separation
color · statusHigh

Don't rely on color alone for status

Order status pills (Trimisă / Pregătire / Gată) are distinguishable mostly by their lime/orange/ink fills. Colorblind staff will need shape or text cues.

Possible directions
  • Pair each status with a small icon (✓, ◷, ●) — the label is already there
  • Or vary the border style (solid vs dashed vs none) so monochrome screenshots still resolve
color · accent on darkLow

Spot-check accent on ink surfaces

The #FF4A1C accent against #15140F ink lands around 4.0:1 — fine for large text but borderline for small mono labels.

Possible directions
  • Reserve accent-on-ink for ≥18px or ≥14px bold (WCAG large-text threshold)
  • For body-size accent text on dark, lighten to a --accentSoft tint with a verified contrast
color · tokensLow

Add a contrast-verified ramp to tokens

Right now contrast is checked at usage sites. Encoding it once in the token layer prevents drift.

Possible directions
  • Document each --ink* opacity with its measured contrast vs. --paper and --paperHi
  • Mark which are valid for body, which for meta-only, in the token comments

How to use this

None of these are blocking. Pick the High-priority items first if time is tight — those are the ones likely to fail a real audit or trip a staff member during service. Everything else is a polish lap that can land alongside other refactors.
